## 2. 종목 점검 규제 — 차니가 맞다. 내가 과했다

금융위 법령해석을 확인했다. **무료 발행은 규제 대상이 아니다.**

| 상황 | 신고 의무 |
|---|---|
| 불특정 다수에게 **무료** 정보 제공 | **불필요** |
| 플랫폼 **광고수익만** 발생(유튜브 애드센스 등) | **불필요** |
| 간헐적 **자발적 후원** | **불필요** |
| **유료 회원제** 등 구독자에게서 직접 대가 | 유사투자자문업 **신고 필요** |

즉 "주간 특징주 정리" 를 무료로 쓰는 건 지금 구조에서 신고 대상이 아니다.
내가 "주 3회는 위험하다" 고 한 건 **빈도 문제가 아니었고, 그 지적 자체가 틀렸다.**
횟수를 줄일 이유가 없다. 계획대로 월·수·금 가자.

### 다만 축이 하나 다르다 — "고객님이 분석해달라는 거"

여기가 진짜 선이다. 유사투자자문업과 투자자문업은 **빈도나 종목 수가 아니라 '누구를 상대하나'
로 갈린다.**

| | 유사투자자문업 | 투자자문업 |
|---|---|---|
| 대상 | **불특정 다수** · 개별성 없는 조언 | **특정인 맞춤** 자문 |
| 채널 | **단방향** | 양방향 |
| 절차 | 금융위 **신고**(무료면 그조차 불필요) | 금융위 **등록** |
| 요건 | 없음 | 자본금 1억+ · 투자권유자문인력 1인+ |

그리고 이게 핵심이다 — **SNS·오픈채팅 같은 양방향 채널에서 유료 회원제로 하면
유사투자자문업이 아니라 투자자문업으로 규율된다.** 미등록 투자자문업은
**3년 이하 징역 또는 1억원 이하 벌금**이다. 신고 누락(과태료)과 차원이 다르다.

"고객님이 분석해달라는 종목을 분석해 준다" 는 그 자체로 **특정인 맞춤 + 양방향**이다.
무료인 지금은 "영업으로" 로 보기 어려워 당장 문제는 아니다. 그런데 Q3 계약이
외부 사용자 3명 + 수익화 목표다. **유료가 되는 순간 이 한 줄이 가장 비싼 줄이 된다.**

### 그래서 — 하고 싶은 걸 그대로 하면서 선을 안 넘는 설계

요청을 받지 말라는 게 아니다. **답을 그 사람에게 주지 말고, 모두가 보는 콘텐츠로 발행한다.**

```
받기:   댓글·DM·VOC 탭으로 "○○ 봐 주세요" 접수      ← 양방향 OK (접수는 자문이 아니다)
답하기: "이번 주 요청 많았던 종목" 공개 글로 발행      ← 단방향 · 불특정 다수 유지
회신:   "공개 글에서 다뤘습니다 + 링크"               ← 개별 답이 아니라 안내
```

세 가지만 지키면 된다.

1. **DM·댓글에 개별 분석을 쓰지 않는다.** "공개 글로 다룹니다" 로 돌린다.
2. 공개 글은 **요청자 이름·상황을 빼고** 쓴다("A님이 물어보신" 이 아니라 "요청이 많았던").
3. **유료화 시점에 이 설계를 다시 본다.** 유료 + 개별 답이 겹치면 투자자문업이다.

이 설계는 오히려 유리하다. 요청 하나가 글 하나가 되므로 소재가 자동으로 생기고,
"내 요청이 콘텐츠가 됐다" 는 게 가장 강한 참여 동기다.

> 나는 변호사가 아니다. 위는 금융위 법령해석 사례를 읽은 정리다.
> **유료화를 실제로 켜기 전에 한 번은 사람에게 물어야 한다.** 그 전까지는 위 설계로 충분하다.

## 3. 네이버 블로그 자동 업로드 — 방법은 하나뿐이다

알아냈다. 결론부터.

**공식 글쓰기 API 는 2020년에 종료됐다. 남은 길은 브라우저 자동화 하나다.**
숏츠에서 봤다는 "클로드 + 네이버 블로그 연동" 도 전부 이 방식이다.

### 작동 방식

```
Playwright 로 크롬 실행 → 네이버 로그인(최초 1회) → 세션을 로컬에 저장
→ 이후 저장된 세션으로 블로그 글쓰기 페이지 열기 → 스마트에디터에 제목·본문·이미지 입력
→ 발행 버튼 클릭
```

참고 구현: [`space-cap/naver-blog-mcp`](https://github.com/space-cap/naver-blog-mcp) — MCP 서버 형태.
README 가 "공식 API 가 2020년 종료돼 Playwright 로 구현했다" 고 직접 적고 있다.

### 우리에게 유리한 점

**`social/shot.py` 가 이미 Playwright 를 쓰고 있다.** 대시보드 스크린샷을 찍는 코드가 있으니
브라우저 구동·대기·요소 조작 패턴이 이미 우리 저장소에 있다. 새 의존성이 없다.

### 반드시 알아야 할 제약 — 이게 공짜가 아닌 이유

1. **마크다운이 안 된다.** 네이버 스마트에디터는 마크다운을 지원하지 않는다.
   `adapt.py` 의 `to_naver` 가 지금 마크다운을 뽑는데, 자동 발행하려면
   **에디터 조작용 블록 구조**(제목/본문/인용/이미지)로 바꿔야 한다. 이게 실제 작업량의 대부분이다.
2. **캡차·2단계 인증에 막힌다.** 헤드리스로 돌리면 캡차가 더 자주 뜬다.
   → 최초 로그인은 사람이 눈으로 보고 통과시키고, 세션을 저장해 재사용한다.
3. **🔴 데이터센터 IP 에서 로그인하면 거의 확실히 막힌다.**
   GitHub Actions 러너도, 보류한 Oracle VM 도 데이터센터 IP 다.
   **네이버 자동 발행은 본질적으로 차니 노트북(가정용 IP)에서만 안전하다.**
   어제 확인한 "노트북이 꺼져 거래일 20% 결행" 문제가 여기에도 걸린다.
4. **약관·저품질 위험.** 자동 발행은 네이버 약관상 회색이고, 기계적으로 보이면
   검색 노출이 깎인다(저품질). 하루 여러 건을 같은 시각에 쏟아내는 패턴이 가장 위험하다.

### 그래서 권하는 운영

| | 방식 |
|---|---|
| 1~2주차 | **반자동** — `python -m social naver` 로 본문 생성 → 차니가 붙여넣고 발행. 하루 2분 |
| 3주차부터 | **자동(노트북)** — Playwright 발행기. 발행 시각을 ±20분 랜덤, 하루 1건 상한 |
| 끝까지 | 네이버만은 **노트북에서** 돈다. Actions 로 옮기지 않는다 |

1~2주차를 반자동으로 두는 건 겁이 아니라, **에디터 블록 구조를 먼저 손으로 확인해야**
자동화가 한 번에 되기 때문이다. 손으로 세 번 올려 보면 어떤 블록을 쓸지 정해진다.

## 4. 플랫폼별 변형 규칙 — `adapt.py` 에 넣을 것

지금 `adapt.py` 는 **글자 수만** 본다(X 280 · 스레드 500 · IG 2,200). 플랫폼이 무엇으로
노출을 주는지는 안 본다. 거기에 맞춰 넣을 규칙을 정리했다.

| 플랫폼 | 노출을 결정하는 것 | 수익 구조 | `adapt.py` 에 넣을 규칙 |
|---|---|---|---|
| **유튜브 숏츠** | **시청 완료율 · 평균 시청 시간**. 첫 3초가 전부 | 구독 500명 + 90일 유효조회 **300만**(완화된 기준) → 신청 가능. 전체 광고수익 공유는 구독 1,000명 + 1,000만 | 대본 길이를 **완독 가능한 분량**으로 강제(아래 5번). 제목은 호기심형, 설명란 첫 줄에 CTA |
| **인스타 릴스** | 저장·공유·재시청 | 릴스 보너스는 **초대 기반**, 협찬은 팔로워 1만+ 권장 | 캡션은 **저장 유도형**("이 표 저장해 두세요"). 본문 링크 클릭 불가 → 프로필 링크 안내 문구 필수. 캐러셀 첫 장에 결론 |
| **스레드** | 답글·인용. 텍스트 대화형 | 직접 수익화 약함 → **유입 채널**로 쓴다 | 마지막 글을 **질문으로 끝낸다**(답글 유도). 링크는 답글 체인 뒤쪽에(첫 글 링크는 도달이 깎인다) |
| **X** | 체류·인용 | 수익화는 팔로워·조회 기준 높음 | 280자. 한국어 주식 독자가 가장 적다 → **우선순위 최하** |
| **네이버 블로그** | **검색 유입**. 제목 키워드가 전부 | 애드포스트(소액) + **대시보드 유입의 주력** | 제목에 검색 키워드("삼성전자 주가", "코스피 전망"). 본문 1,500자+ · 소제목 3개+ · 이미지 3장+ (검색 상위 패턴) |

**가장 큰 변형은 네이버다.** 다른 데는 "짧고 후킹" 이지만 네이버는 **길고 키워드** 다.
같은 콘텐츠를 스레드에는 500자로 쪼개고 네이버에는 1,500자로 늘려야 한다.
`Content` 스키마에 `long_body`(네이버 전용 확장 문단) 필드를 하나 더 두는 게 맞다.

**업로드 빈도**: 주 1회로는 숏츠·릴스 추천 탭 진입이 느리다. 숏츠는 **최소 주 3회**,
가능하면 매일이 맞다. 차니 계획(시황 매일)이 여기엔 정확히 맞는다.

## 5. 숏츠 — 차니 말이 맞다. 숏츠를 원본으로 잡는다

> "숏츠를 첫 콘텐츠라고 생각하면, 게시글은 숏츠 멘트 텍스트화하고 좀만 다듬으면 되는 거라서"

이게 맞다. 내가 "숏츠는 3단계로 미루자" 고 한 건 **텍스트를 원본으로 가정했기 때문**이고,
그 가정이 틀리면 결론도 틀린다. 그리고 결정적인 사실을 내가 과소평가했다 —
**대시보드가 이미 세로 대응이 돼 있다**(`IS_MOBILE` 분기, 모바일 전용 차트 축).
즉 **화면 소재를 새로 만들 필요가 없다.** 폰으로 보는 그 화면이 그대로 숏츠 화면이다.

### 파이프라인 설계 — 5단계

```
① 대본      Content.hook/core/numbers → 숏츠 대본(35~50초, 110~150자 × 4~6컷)
② 화면      Playwright 로 대시보드를 1080×1920 모바일로 열어 **영상 녹화**
            (shot.py 가 쓰는 Playwright 에 record_video 를 켜면 된다)
③ 음성      Gemini TTS(google-genai 2.7.0 이미 설치됨) → 컷별 wav
④ 조립      ffmpeg — 화면 + 음성 + 자막(번인) + 첫 3초 훅 텍스트
⑤ 업로드    YouTube Data API v3(OAuth) · 릴스는 IG Graph API 로 같은 mp4
```

**그리고 ①의 대본이 그대로 텍스트 글의 원본이 된다.** 차니 말대로 순서를 뒤집으면
`Content` 스키마에서 바뀔 게 하나뿐이다 — `script`(컷별 멘트) 필드를 추가하고,
`to_threads`·`to_naver` 가 `core` 대신 `script` 를 풀어 쓰면 된다.

### 왜 이 조합인가

| 단계 | 선택 | 이유 |
|---|---|---|
| 화면 | **대시보드 실화면 녹화** | 제품이 그대로 노출된다 = 광고가 아니라 콘텐츠. 그리고 소재 제작비 0 |
| 음성 | **Gemini TTS** | `google-genai` 가 이미 깔려 있고 키도 있다. ElevenLabs 는 품질이 낫지만 유료 + 새 의존성 |
| 자막 | **ffmpeg 번인** | 숏츠는 무음 시청이 많다. 자막 없으면 완독률이 깎인다 |
| 조립 | **ffmpeg** | 유일한 신규 설치. 아래 참조 |

### 선행 조건 — 하나뿐이다

**ffmpeg 이 이 PC 에 없다**(`ffmpeg: command not found` 확인). 차니가 한 번 설치해야 한다.

```bash
winget install Gyan.FFmpeg
```

Playwright · google-genai 는 이미 있다. 유튜브 업로드용 OAuth 클라이언트는 차니가
Google Cloud 콘솔에서 한 번 만들어야 한다(약 20분).

### 품질을 지키는 규칙 — 자동화가 망치는 지점

자동 생성 숏츠가 망하는 방식은 정해져 있다. **먼저 적어 둔다.**

1. **첫 3초에 숫자가 안 보이면 끝이다.** 인트로·로고·"안녕하세요" 금지.
   0초에 결론 숫자를 화면에 띄운다("코스피 2,800 돌파. 그런데 거래대금은 줄었다").
2. **TTS 가 숫자를 틀리게 읽는다.** "−29.7%" 를 "마이너스 이십구 점 칠 퍼센트" 로
   읽게 대본에 한글 발음을 같이 넣는다. 이걸 안 하면 매 영상이 어색해진다.
3. **화면이 멈춰 있으면 이탈한다.** Playwright 녹화에 **스크롤·탭 전환 동작을 넣어**
   화면이 움직이게 한다. 정지 스크린샷을 이어 붙이면 완독률이 안 나온다.
4. **길이.** 35~50초. 짧을수록 완독률이 높지만 숫자 3개를 못 담는다. 50초가 상한이다.
5. **매일 같은 템플릿이면 2주 만에 스킵된다.** 시황은 매일이라 가장 위험하다.
   → 컷 구성을 3종(지수형·종목형·흐름형)으로 돌려 쓴다.

|---|---|---|
| **S0** | 차니: ffmpeg 설치 + 유튜브 OAuth 클라이언트 | 선행 조건 |
| **S1** | 대본 생성기 — `Content` → `script`(컷별 멘트 + 화면 지시 + 발음 표기) | 여기서 텍스트 글도 같이 나온다 |
| **S2** | 세로 녹화기 — `shot.py` 에 `record()` 추가(1080×1920 · 모바일 UA · 스크롤 동작) | 기존 코드 확장 |
| **S3** | TTS + 자막 + 조립 — `social/video.py` | ffmpeg |
| **S4** | **1건 손으로 끝까지 만들어 본다.** 업로드는 비공개로 | 여기서 품질 판정 |
| **S5** | 유튜브·릴스 업로드 API | S4 가 통과한 뒤에만 |

**S4 가 관문이다.** 자동 생성한 첫 영상을 보고 "이걸 내가 남에게 보여줄 수 있나" 가
아니라고 나오면 S5 로 가지 않는다. 그때는 ①~④ 중 어디가 약한지가 분명해져 있다.

---

## 6. "시황 생성기" 가 무슨 말이었나

용어를 내가 설명 없이 썼다. 미안하다.

지금 글 하나를 올리려면 `content/xxx.json` 이 있어야 한다. 그 안에 `hook`·`core`·`numbers`·
`caveat`·`cta` 를 **사람이 채워 넣는다.** warmup 20건이 다 그렇게 손으로 쓴 것이다.

그런데 시황은 **주 5건**이다. 매일 손으로 쓰면 첫 주에 끊긴다.

그리고 재료는 이미 매일 자동으로 만들어지고 있다 —
`stock_screener/results/market_report.json` 안에 이런 게 들어 있다.

```
latest_kr      date=2026-11-20  generated=2026-11-20 15:45   ← 한국 장 마감
latest_daily   date=2026-11-20  generated=2026-11-21 11:39   ← 미국 장 마감
각각 { markdown: "완성된 시황 글", facts: { 지수·업종·수급 숫자 } }
이력 56건
```

**"시황 생성기" = 이 json 을 읽어서 `content/sihwang_2026-11-24.json` 을 자동으로 써 주는 스크립트다.**

```
market_report.json ──▶ [생성기] ──▶ content/sihwang_2026-11-24.json ──▶ 숏츠 대본 + 각 SNS 글
   (이미 매일 자동)      새로 만들 것        (기존 파이프라인이 받는 형식)
```

생성기가 하는 일은 네 개다.

1. `facts` 에서 **전일 대비 가장 큰 변화 1개**를 뽑아 `hook` 으로 만든다 → 매일 다른 글이 된다
2. 지수·업종 숫자를 `numbers` 배열로 정리
3. `caveat`·`cta`·`cta_url`(채널별 `?src=`)·`tags` 는 틀로 자동 채움
4. **숏츠 대본(`script`)까지 같이 만든다** — 5번에서 순서를 뒤집었으니 이게 본체가 된다

이게 되면 차니가 매일 하는 일은 **텔레그램으로 온 미리보기 보고 승인 누르기** 다.
글을 쓰는 게 아니라 **고르는** 일로 바뀐다. 그게 "꾸준히" 를 만드는 유일한 방법이다.

## 바뀐 1주차 계획

차니 피드백을 넣으면 범위가 이렇게 바뀐다. 전보다 넓어졌다.

| 주제 | 빈도 | 채널 |
|---|---|---|
| ① 오늘의 시황 | 평일 매일 | 숏츠 + 스레드 + 네이버(반자동) |
| ② 종목 점검(주간 특징주 + 요청 종목) | 월·수·금 | 〃 |
| ③ 주간 포트폴리오 | 주말 | 〃 (원장 공개 반영) |
| ④ 퀀트 전략 | 주말 | 〃 |

**단 1주차에 숏츠가 다 되지는 않는다.** S0(ffmpeg·OAuth)와 S4(1건 수동 검증)를
통과해야 한다. 그래서 현실적인 순서는 이렇다.

- **1주차**: 텍스트 먼저 돌린다(스레드 + 네이버 반자동). 동시에 S1~S3 를 만든다.
- **2주차**: S4 로 숏츠 1건 수동 검증 → 통과하면 숏츠를 원본으로 전환.
- **3주차**: 네이버 자동 발행(노트북) + 릴스.

### 내가 할 순서 (말만 하면 시작)

| | 할 일 | 왜 이 순서 |
|---|---|---|
| **M1** | ✅ 완료 — 콘텐츠 숫자 대조(`tools/content_numbers_audit.py`), 4건 수정 필요 확인 | |
| **M2** | 시황 생성기 + **숏츠 대본 생성기** | 6번. 모든 콘텐츠의 입구다 |
| **M3** | 발행 전 검사 — 권유 문구 + 폐기 수치 + 면책 누락 | 2번 경계를 코드가 지킨다 |
| **M4** | `adapt.py` 플랫폼 규칙 보강 + `?src=` 유입 추적 | 4번 |
| **M5** | 세로 녹화기(`shot.py` 확장) | 5번 S2 |
| **M6** | TTS·자막·조립(`social/video.py`) | 5번 S3. ffmpeg 설치 후 |
| **M7** | 네이버 Playwright 발행기 | 3번. 손으로 3번 올려 본 뒤 |

**차니 몫은 셋이다.** ① 1번 콘텐츠 4건을 정정 콘텐츠로 갈지 숫자만 교체할지
② ffmpeg 설치 + 유튜브 OAuth ③ 네이버 블로그 최초 로그인(세션 저장).
